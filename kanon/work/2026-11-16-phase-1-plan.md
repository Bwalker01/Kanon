# Phase 1: Core Engine

> **Summary:** Build the `kanon` command: project setup, templates, the review loop, approvals,
> verification and cost reporting, then prove it on two real requirements in this repository.
> **Decision:** Plan approved by the owner on 2026-11-16 (R-2). Build in progress.

## 1. Plan

| Role | Who |
|---|---|

### 1.1 Outcome

After Phase 1, `kanon init` prepares any Git repository for Kanon. A request made in Claude Code
then passes through the full loop: requirement, plan, build, independent review, correction,
documentation and owner approval. `kanon verify` fails if any step is missing.

### 1.6 P1-05 Design (2026-11-19)

| Part | Design |
|---|---|
| Approved material | Plan approval: the title and Plan; result approval: the title to the end of the Review; item approval (`--item`): the item's Work Items row, Plan subsections naming it and Review rows naming it. Frontmatter, summary block and Actions are left out; SHA-256 of that text, plus the commit at approval |
| Record | A row in the Decision table: item, `Approved` or `Changes requested`, date, and a basis giving the form, the approver's GitHub username, the commit and `sha256:<hash>` |
| Forms | `kanon approve <work>` run by the person ("approved by"), or `kanon transcribe <work> --quote "<the person's words>"` run by the assistant ("transcribed"); both hashed alike (owner, 2026-11-19) |
| Other commands | `kanon request-changes <work> "<text>"`; `--plan` on `approve` sets status `in-progress`, otherwise `complete`; `--item P1-05` approves one item and leaves the status (K-340); late-review rows get "Owner reviewed <date>" before hashing |
| `kanon verify` | Fails when the latest approval of each plan, result or item no longer matches its hash, when a recorded approval's hash is missing or malformed, when a code fence is never closed, when the approver is not in `approvers`, or when a `complete` file's latest approval has no hash and is dated after 2026-11-19; earlier rows without a hash pass as legacy |
| Self-approval | `kanon sync` writes Claude Code deny rules for `Bash(kanon approve:*)`, `Bash(kanon request-changes:*)`, and edits to `kanon/kanon.toml` (exceptions and approvers are owner-only, K-33); `kanon approve` also refuses when `CLAUDECODE` is set |
| Reviewer writes (K-29) | If Claude Code's hook input identifies the subagent, the guard blocks file-writing commands for `kritos-reviewer`; otherwise the gap is reported as found |
| Bypasses | Shell edits of any file (including `.claude/settings.local.json`), an unset `CLAUDECODE`, forged transcriptions, forged hashless rows dated on or before 2026-11-19, and reviewer writes through programs or unresolved variables remain possible (L-001); listed in ADR-013 as tamper-evident only, with P1-10's App as the tamper-proof form |
| Records | ADR-013 amends ADR-003 ("the assistant never records an approval") to allow labelled transcription |

### 1.7 P1-09 Design (2026-11-19)

| Part | Design |
|---|---|
| Names | Plan branch `kanon/<work>/plan`; item branches `kanon/<work>/<item>`, where `<work>` is the work file name without its date (owner, 2026-11-19: Git cannot hold `kanon/<work>` beside `kanon/<work>/<item>`) |
| Commands | `kanon branch start <work> [<item>]` creates the plan branch from the current commit if missing, then the item branch from the plan branch, and switches to it; `kanon branch merge <work> <item>` merges an item into the plan branch; `kanon branch status <work>` lists items, their branch, review state and whether merged |
| Reviewed | The latest Decision row for the item decides first: a change request refuses; a labelled approval by a listed approver whose hash matches allows. Otherwise the latest Review row naming the item must be `pass`, with no blocking findings, not awaiting the owner. Either way the latest Review row must cite the item branch's tip commit, so commits added after review need a new review (K-382, K-383) |
| Where records live | Work files are edited on the plan branch only, so parallel items never conflict on the Review table; `merge` refuses an item branch that changed `kanon/work/` |
| Merging | `git merge --no-ff` only; never rebase, squash, reset or force. A conflict aborts the merge and reports the files; nothing is left half-merged |
| Mechanical check | `kanon init` adds a `pre-merge-commit` hook that refuses a merge into `kanon/<work>/plan` of an item that is not reviewed; `kanon branch start` sets `--no-ff` as the plan branch's merge option so the hook always runs (K-380), and `kanon verify` (the pre-commit hook) refuses committing a merge in progress that the hook refused (K-381). Git 2.43 has not written `MERGE_HEAD` when the hook runs, so the hook reads the merged branch from `GIT_REFLOG_ACTION` (tested). Documented bypasses: `--no-verify`; `git merge --ff`; merging an item's commit by its hash, or through a renamed or copied branch outside `kanon/<work>/`; a preset `GIT_REFLOG_ACTION`; cherry-picking; a repository where `kanon` is not installed, where the hook only prints a note |
| Shared records | Decision records and learnings added by two items can still conflict when both merge (assessment, not tested) |
| For P1-10 | Each item arrives as a merge commit, so the pull request can list items and rounds; the plan branch must merge into `main` without squashing or rebasing (K-52); the description reuses `review_state` (K-392) |
| Limits | Local branches only; pushing and pull requests are P1-10. This session may push only its assigned branch, so the commands are proven in temporary repositories by tests |

### 1.8 P1-10 Design (2026-11-20)

| Part | Design |
|---|---|
| Identity | One GitHub App per organisation or person, created by a person; `app_id` and `app_slug` in `[github]` of `kanon/kanon.toml` (owner, 2026-11-20); a standalone Kanon-managed App is a later phase |
| Key | `KANON_APP_KEY` (PEM or base64 PEM) in cloud environments; `~/.config/kanon/github-app.pem` (mode 600) on a person's computer. Never in the repository, chat or command output |
| Tokens | A 10-minute JWT signed with the key finds the repository's installation and requests a 1-hour installation token limited to this repository and to contents, pull requests and metadata. Tokens stay in memory |
| Setup | `kanon github setup`, run locally by the person: GitHub's App Manifest flow with a redirect to a local port, then the key is saved and `kanon.toml` filled, then the install page opens. First setup is local only (owner). `kanon github check` reports the key, installation and permissions anywhere |
| Pull requests | `kanon github pr <work>` pushes `kanon/<work>/plan` with the App token and opens or updates one pull request into `main`. The description is generated without a model call: items with their merge commits, review rounds and cost |
| Reviewer notes | `kanon github notes <work>` posts Kritos's findings as a comment-only review from the App; Kanon never submits an approving review |
| Approvals back | The pull request's merge is the final approval; no approval row is written after it (owner, 2026-11-20). When Kanon opens the pull request it adds a Decision row "Approved on merge of pull request #N" and leaves the work `awaiting-approval`; `kanon verify` and the Desk treat it as decided only once that pull request's merge commit is in Git history (K-400, K-402), and a pull request closed without merging reopens the work (K-401). `kanon github sync` records change requests as rows, and keeps open pull requests in `kanon/local/` so the Desk lists them without a network call |
| Owner's login | Agents never act as the owner on GitHub (owner, 2026-11-19): `kanon sync` adds deny rules for the GitHub connector's writing tools, and the guard blocks `gh` commands that write. The session's clone and the harness's own branch pushes still use the owner's connection (recorded limit) |
| Protection | `kanon github protect`, run by the person with their own `gh` login and refused inside an assistant session: `main` requires one approving review from a code owner (`CODEOWNERS` lists the approvers); administrators may bypass, so the owner can merge their own pull requests (owner, 2026-11-23, K-404); no force push or deletion, and the repository allows merge commits only (K-52, K-392). The App has no Administration permission |
| Actions | None; every call runs locally (ADR-007) |
| Records | ADR-014 amends ADR-007 (identity, key, owner's login) |
| Limits | Tested 2026-11-20: this cloud session's agent proxy refuses GitHub App API paths (`GET /app`: "Access to this GitHub API path is not permitted through this proxy"), so the App cannot sign in from Claude Code cloud sessions; the key is readable by commands in cloud sessions (owner accepted); GitHub Enterprise Server API differences are untested; this session's harness permits pushing only its own branch, so pushing `kanon/*` here needs the owner's permission |

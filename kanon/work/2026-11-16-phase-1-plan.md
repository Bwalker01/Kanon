# Phase 1: Core Engine

> **Summary:** Build the `kanon` command: project setup, templates, the review loop, approvals,
> verification and cost reporting, then prove it on two real requirements in this repository.
> **Decision:** Plan approved by the owner on 2026-11-16 (R-2). Build in progress.

| Role | Who |

### 1.1 Outcome

After Phase 1, `kanon init` prepares any Git repository for Kanon. A request made in Claude Code
then passes through the full loop: requirement, plan, build, independent review, correction,
documentation and owner approval. `kanon verify` fails if any step is missing.

### 1.6 P1-05 Design (2026-11-19)

| Part | Design |
|---|---|
| Approved material | Plan approval: the title and Plan; result approval: the title to the end of the Review; item approval (`--item`): the item's Work Items row, Plan subsections naming it and Review rows naming it. Frontmatter, summary block and Actions are left out; SHA-256 of that text, plus the commit at approval |
| Record | A row in the Decision table: item, `Approved` or `Changes requested`, date, and a basis giving the form, the approver's GitHub username, the commit and `sha256:<hash>` |
| Forms | `kanon approve <work>` run by the person ("approved by"), or `kanon transcribe <work> --quote "<the person's words>"` run by the assistant ("transcribed"); both hashed alike (owner, 2026-11-19) |
| Other commands | `kanon request-changes <work> "<text>"`; `--plan` on `approve` sets status `in-progress`, otherwise `complete`; `--item P1-05` approves one item and leaves the status (K-340); late-review rows get "Owner reviewed <date>" before hashing |
| `kanon verify` | Fails when the latest approval of each plan, result or item no longer matches its hash, when a recorded approval's hash is missing or malformed, when a code fence is never closed, when the approver is not in `approvers`, or when a `complete` file's latest approval has no hash and is dated after 2026-11-19; earlier rows without a hash pass as legacy |
| Self-approval | `kanon sync` writes Claude Code deny rules for `Bash(kanon approve:*)`, `Bash(kanon request-changes:*)`, and edits to `kanon/kanon.toml` (exceptions and approvers are owner-only, K-33); `kanon approve` also refuses when `CLAUDECODE` is set |
| Reviewer writes (K-29) | If Claude Code's hook input identifies the subagent, the guard blocks file-writing commands for `kritos-reviewer`; otherwise the gap is reported as found |
| Bypasses | Shell edits of any file (including `.claude/settings.local.json`), an unset `CLAUDECODE`, forged transcriptions, forged hashless rows dated on or before 2026-11-19, and reviewer writes through programs or unresolved variables remain possible (L-001); listed in ADR-013 as tamper-evident only, with P1-10's App as the tamper-proof form |
| Records | ADR-013 amends ADR-003 ("the assistant never records an approval") to allow labelled transcription |

### 1.7 P1-09 Design (2026-11-19)

| Part | Design |
|---|---|
| Names | Plan branch `kanon/<work>/plan`; item branches `kanon/<work>/<item>`, where `<work>` is the work file name without its date (owner, 2026-11-19: Git cannot hold `kanon/<work>` beside `kanon/<work>/<item>`) |
| Commands | `kanon branch start <work> [<item>]` creates the plan branch from the current commit if missing, then the item branch from the plan branch, and switches to it; `kanon branch merge <work> <item>` merges an item into the plan branch; `kanon branch status <work>` lists items, their branch, review state and whether merged |
| Reviewed | An item may merge when the plan branch's work file holds an item approval for it (P1-05) whose hash matches, or when its latest Review row naming it has verdict `pass` and no outcome marked "Owner decides" without "Owner reviewed" |
| Where records live | Work files are edited on the plan branch only, so parallel items never conflict on the Review table; `merge` refuses an item branch that changed `kanon/work/` |
| Merging | `git merge --no-ff` only; never rebase, squash, reset or force. A conflict aborts the merge and reports the files; nothing is left half-merged |
| Mechanical check | `kanon init` adds a `pre-merge-commit` hook that refuses a merge into `kanon/<work>/plan` of an item that is not reviewed, so a plain `git merge` is refused too. Git 2.43 has not written `MERGE_HEAD` when the hook runs, so the hook reads the merged branch from `GIT_REFLOG_ACTION` (tested). `--no-verify`, and merging an item's commit by its hash rather than its branch, remain documented bypasses |
| Limits | Local branches only; pushing and pull requests are P1-10. This session may push only its assigned branch, so the commands are proven in temporary repositories by tests |
